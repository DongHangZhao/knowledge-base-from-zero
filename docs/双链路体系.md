# 双链路体系：文件链路 + 索引链路

**简体中文** ｜ [English](dual-pipeline.en.md)

> 只看 `raw + wiki`，你看到的是**一套目录**；
> 加上 `md → SQLite`，你才得到**一套能被 AI 稳定检索的知识库**。
> 本文讲清两条链路各自是什么、怎么对齐、以及只做第一条会出什么事。

---

## 一、先看全景

```
┌──────────────────────── 链路 A · 内容链路（真相源）────────────────────────┐
│                                                                            │
│   raw/                     wiki/                      outputs/             │
│   不可变原件    ──提炼──▶   合成知识      ──产出──▶    交付物               │
│   PDF/图/视频              md 文章                    报告/图表            │
│   （只读，永不删）          （可随意改写）              （会覆盖）            │
│                                                                            │
└────────────────────────────────┬───────────────────────────────────────────┘
                                 │  build（增量，按 content_hash）
                                 ▼
┌──────────────────────── 链路 B · 索引链路（派生层）────────────────────────┐
│                                                                            │
│   kb.db  (SQLite，单文件)                                                   │
│   ├── docs           整篇元数据：path / title / hash / mtime                │
│   ├── docs_fts       FTS5 整篇倒排索引（bm25 排序）                          │
│   ├── doc_terms      TF-IDF 词项倒排（余弦相似度）                           │
│   ├── chunks         按标题层级切块（带「父标题 > 子标题」路径）             │
│   ├── chunks_fts     FTS5 分块倒排索引                                      │
│   └── raw_metadata   原件元数据（只存元信息，不存正文）                      │
│                                                                            │
│   search ──▶ 整篇 ⊕ 分块 RRF 融合 ──▶ 一律落回 doc.path                     │
│                                                                            │
└────────────────────────────────────────────────────────────────────────────┘
                                 │
                                 ▼
                      AI 拿到的不是「一段文字」，
                     而是「一段文字 + 它来自哪个文件第几节」
```

**一句话分工**：
链路 A 保证**知识不丢、可 diff、可迁移**；链路 B 保证**AI 找得到、引得到、不瞎编**。

## 二、只做链路 A，会遇到什么

很多人（包括我一开始）觉得 `raw + wiki` 就够了，加个 `index.md` 当目录。500 篇以内还能撑，再往上会依次撞四堵墙：

| 现象 | 根因 | 后果 |
|---|---|---|
| AI 说「根据 `wiki/技术/xxx.md`」但文件不存在 | 它是凭记忆拼路径，不是查出来的 | **幽灵引用**，你按路径点开是 404 |
| AI 回答得很泛、答不到点上 | 只读了 `index.md` 的标题，没读正文 | 答案正确但无用 |
| 把整篇 5000 字塞进上下文 | 没有分块，只能整篇喂 | token 成本 ×10，还容易超窗 |
| 明明库里有，AI 说没有 | 关键词在正文里，标题里没有 | 该复用的知识没复用上 |

**索引不是「方便功能」，是「AI 能引用原文」的前提。**
没有链路 B，AI 只有两条路：猜路径（幻觉）或整篇读（烧钱）。

## 三、链路 A：内容链路

### 3.1 三个区，三种生命周期

| 区 | 内容 | 写权限 | 生命周期 |
|---|---|---|---|
| `raw/` | 下载的原件：PDF、图片、视频、docx、网页存档 | **只增不改** | 永久保留，永不删 |
| `wiki/` | 读 `raw/` 后写成的可读知识（md） | AI + 人可改写 | 持续迭代，允许重写 |
| `outputs/` | 报告、图表、导出文件 | 每次覆盖 | 可随时清空重建 |

**为什么必须分开**：
- 原件与合成稿混在一起 → 改错一次，源头就没了；
- 能力与产物混在一起 → 脚本被一堆报表淹掉；
- 三者混在一个目录 → 想「清空产物」时不敢动手，因为分不清哪个是原件。

### 3.2 合成稿必须能追溯

`wiki/` 里每一篇合成稿都要挂一行来源：

```markdown
> Raw: raw/技术/2026-10-01-某论文.pdf
```

这不是形式主义——它是**链路 A 与链路 B 之外的第三条保险**：哪天你怀疑某个结论，
能一路点回原件。没有这行，半年后你自己都不敢用自己写的东西。

## 四、链路 B：索引链路

### 4.1 六张表，各管一件事

```sql
-- 整篇粒度
CREATE TABLE docs(
  id INTEGER PRIMARY KEY,
  path TEXT UNIQUE NOT NULL,   -- 🔴 唯一连接键，与链路 A 的文件相对路径一致
  title TEXT,
  mtime REAL,
  size INTEGER,
  content_hash TEXT,           -- 增量判断依据（sha1 of body）
  body TEXT NOT NULL
);

CREATE VIRTUAL TABLE docs_fts USING fts5(
  path UNINDEXED, title, body, tokenize='unicode61'
);
-- bm25(docs_fts) 越低越相关；短语查询要加引号

CREATE TABLE doc_terms(          -- 生产版才有：TF-IDF 稀疏向量
  term TEXT, doc_path TEXT, tf INTEGER, weight REAL
);

-- 分块粒度
CREATE TABLE chunks(
  id INTEGER PRIMARY KEY,
  doc_path TEXT NOT NULL,
  heading TEXT,                 -- 「一级标题 > 二级标题」，命中后能告诉 AI 在哪一节
  ord INTEGER,                  -- 同篇内顺序，便于拼接上下文
  body TEXT NOT NULL
);

CREATE VIRTUAL TABLE chunks_fts USING fts5(
  doc_path UNINDEXED, heading, body, tokenize='unicode61'
);

-- 原件元数据（关键设计：不存正文）
CREATE TABLE raw_metadata(
  path TEXT PRIMARY KEY, ext TEXT, size INTEGER,
  mtime REAL, sha1 TEXT, title TEXT
);
```

### 4.2 为什么 `raw/` 只入元数据

原件是 PDF / 图片 / 视频，动辄几百 MB。把它们全文抽出、切块、入索引，成本极高，收益却很低——
你 90% 的检索需求是「我到底有没有这份资料」，而不是「这份 PDF 第 37 页写了什么」。

所以：**`raw/` 存元数据（能不能找到），`wiki/` 存全文（内容是什么）**。
真要读 PDF 正文，按需抽取，不要预建。

### 4.3 为什么要分块，又为什么不能只用分块

- **只用整篇**：命中后只能把 5000 字全给 AI，精度差、成本高；
- **只用分块**：丢了全文词频信号，实测 Recall@5 掉约 2 个点；
- **两路融合**：整篇掌握「这篇讲什么」，分块掌握「哪一节最密」，**RRF 融合后 MRR 提升约 2.2%**。

融合公式（Reciprocal Rank Fusion）：

```
score(doc) = Σ_over_lists  1 / (k + rank_in_list)      # k 通常取 60
```

关键点：**RRF 只吃排名，不吃原始分数**——因为 bm25 分值和余弦分值量纲不同，直接加权会互相污染。

### 4.4 对齐机制：`doc.path` 是唯一连接键

两条链路之间**没有外键、没有同步服务**，只有一个约定：

> `docs.path` = 文件相对知识库根的路径，正斜杠，不含 `./` 前缀。

所有检索结果最终都归一到这个键，所以：
- 整篇命中、分块命中、向量命中 —— 统一落回同一个 `path`；
- Recall 口径一致，不同检索模式可以直接对比；
- AI 拿到结果就能拼出可点击的路径。

## 五、最小可运行实现（约 160 行，纯标准库）

代码在 [`examples/mini_index.py`](examples/mini_index.py)，只依赖 Python 自带的 `sqlite3`。
它实现了三件事：**增量建库 / 整篇⊕分块融合检索 / 结果带路径**。

### 5.1 建库

```bash
python docs/examples/mini_index.py build --kb-root . --db mini_kb.db
```

实测输出（拿本仓库自己的 38 篇 md 当语料）：

```
[build] new=38 upd=0 same=0 del=0 -> mini_kb.db
```

### 5.2 检索

```bash
python docs/examples/mini_index.py search "双链路" --db mini_kb.db --topk 2
```

```
1. docs/双链路体系.md   [0.0479]
   …README.md   [0.0328]
   …` 是真相源，其它工具的约定文件只做「转发层」指回它。

### 🔴 [[双链路]]：文件链路 + 索引链路

很多人只看到…
```

注意结果里的两个细节：**命中词被方括号标出**、**结果第一行是文件路径**。
后者是硬要求：AI 引用时必须能落到文件。

### 5.3 统计与增量

```bash
python docs/examples/mini_index.py stats --db mini_kb.db
# docs=38 chunks=336 fts_rows=38
# db_size=1396.0 KB
# built_at=2026-10-21 17:58:12

python docs/examples/mini_index.py build --kb-root . --db mini_kb.db
# [build] new=0 upd=0 same=38 del=0    ← 增量生效，一秒内跑完
```

## 六、从最小实现到生产

最小实现能跑，但不够用。生产版（仓库作者自用版本）在五处做了加强：

| 维度 | 最小实现 | 生产版 | 为什么 |
|---|---|---|---|
| 中文分词 | SQLite `unicode61`（按字切） | **jieba**（精确 / 搜索模式） | 按字切召回高但精度差；jieba 搜索模式在向量路上 Recall@1 从 32% → 43% |
| 稀疏向量 | 无 | **TF-IDF + 余弦** | 关键词路之外多一路词袋信号 |
| 稠密向量 | 无 | **LSA 128 维**（默认）/ BGE 512 维（深度） | 治「说法不同但意思相同」的查询 |
| 评测 | 无 | **人工 100 + 自动 70 条 × 8 路**，Recall@5 / MRR@5 | 没有评测的检索优化 = 玄学 |
| 自检 | 无 | **周自检 + 退出码门禁** | 索引悄悄坏掉比明显报错更可怕 |

**实测对照（人工 100 条评测集）**：

| 检索路径 | Recall@5 | MRR@5 |
|---|---|---|
| 关键词 ⊕ LSA 稠密向量（默认） | 93–94% | **0.8525–0.8595** |
| 关键词粒度融合（整篇 ⊕ 分块） | 94.0% | 0.8440 |
| FTS5 整篇单路 | 94.0% | 0.8212 |
| 分块单路 | 92.0% | 0.7828 |
| TF-IDF 稀疏单路 | 77.0% | 0.5152 |

两条硬结论（踩出来的，不是推出来的）：

1. **弱路不升级，混合就是负优化** —— TF-IDF 比 FTS5 差 17 个点，硬融合后 Recall 反而掉 4 个点；
   LSA 只差 3 个点，融合就是双赢。**混合能不能赢，取决于两路质量是否接近。**
2. **BGE 只在难例上有效** —— 语义难题命中从 0/5 提升到 1/5，但整体 Recall 反而略降，
   延迟 19.8ms（关键词路 0.7ms）。**为 0.3% 的提升换 28 倍延迟，不划算**，所以只留作深度兜底。

## 七、三条铁律

### 铁律 1：SQLite 是派生层，不是真相源

- `kb.db` 可以**随时删除**，重跑 `build` 就回来了；
- 永远**不要手改** `kb.db` 里的内容——改了下次 build 就被覆盖，而且没人知道改过；
- 备份策略要的是「能重建」，不是「备份 db 文件」（不过生产版仍会滚动备份，因为重建要花时间）。

判断标准很简单：**如果 db 和 md 冲突，永远以 md 为准。**

### 铁律 2：索引与分词器绑定

FTS5 的分词器在**建库时**就固化了。后来换 jieba、改环境变量、升级 SQLite，
**必须全量重建**，否则：

- 建库时按「字」切 → 查询时按「词」切 → token 对不上 → 命中率腰斩
- 而且它**不报错**，只是悄悄查不准。

### 铁律 3：命中必须能落回文件路径

检索结果如果只有「一段文本」，AI 没法引用，你也没法核对。
所以每一层命中（整篇 / 分块 / 向量）都要归一到 `doc.path`，
再配上 `heading`，AI 才能写出「见 `wiki/技术/xxx.md` 的『四、索引』一节」。

## 八、七个坑（都是真踩过的）

1. **FTS5 external content 表不能直接 DELETE** —— 报 `no such column: T.tokens`。
   解决办法：用普通 FTS5 表（内容自存），删的时候 `DELETE FROM fts WHERE path=?`。

2. **SQL 注释只能用 `--`** —— 写 `#` 会当成语法错误。这个坑在跨语言写脚本时最容易犯。

3. **等权 RRF 会被弱路稀释** —— 见第六节。弱路要么升级，要么别融。

4. **加了索引不一定被用** —— 两个最左前缀重复的索引，规划器只走其中一个。
   用 `EXPLAIN QUERY PLAN` 验尸，删掉冗余索引后体积 -7.3%、同查询快 21%。

5. **WAL 模式下不能直接 `cp kb.db`** —— WAL 里的内容会丢。
   备份要用 `VACUUM INTO 'backup.db'`。

6. **分块单独用是负优化** —— 丢了全文词频。要和整篇融合用。

7. **`content_hash` 必须用正文计算，不能用 mtime** ——
   `touch` 一下文件、同步盘改个时间戳，mtime 变了内容没变，白重建一遍；
   反过来，脚本批量替换内容但保留 mtime（`copy2`），内容变了却跳过了更新 —— **索引就开始撒谎**。

## 九、自检清单（改完索引代码后逐条过）

- [ ] `build` 后 `stats` 的文档数 = `find . -name "*.md" | wc -l` ？

- [ ] 连续 `build` 两次，第二次是否全部「未变」？

## 十、FAQ

**Q：为什么不直接用向量库（Chroma / FAISS / Qdrant）？**
可以，而且语义召回确实更好。但代价是多一个服务、多一份依赖、索引和文件更容易不同步。
本体系选择「SQLite 单文件 + 可选向量路」，理由是**单个文件能跟知识库一起搬走**——
换电脑、拷 U 盘、进 git LFS，都不需要重装环境。规模到十万篇再换不迟。

**Q：`outputs/` 要不要入索引？**
默认**不入**。产物是会被覆盖的中间态，进索引会污染检索结果（同一份报告出现十个版本）。
真要检索产物，单独建一个库。

**Q：索引多久重建一次？**
内容改动后立刻增量 `build`（毫秒级）。全量重建只在换分词器、改表结构、库损坏时做。

**Q：能不能不写代码，用现成工具？**
能。Obsidian + 全文搜索插件、Logseq、甚至 `rg` 都行。
但只要你希望 **AI 能引用「第几节」**，就需要分块 + 标题路径 + 路径回填——
这三件事现成笔记软件基本不提供，所以这里选择自己建库。
