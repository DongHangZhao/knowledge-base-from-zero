# 检索层设计与评测方法

**简体中文** ｜ [English](retrieval-engine.en.md)

> 本文讲的是「怎么给个人知识库搭一层真正能用的检索」，以及**怎么证明它是对的**。
> 它不是 API 文档，是**设计取舍 + 评测方法 + 踩坑记录**。
> 所有数字都来自真实运行，不是估算；每个关键结论后面都标了「怎么验证的」。

---

## 0. 先说什么情况不该自己做

检索层不是必选项。**先问三个问题**：

1. **你的库有多大？** 几百篇以内，`grep` + 一份好的目录结构就够，别上检索引擎。
2. **能不能接受出网？** 能出网且不介意数据出境，用托管方案最省事。
3. **有没有人维护？** 自建检索层是要维护的（分词器、索引重建、版本升级）。

**本文适用于**：数据在几千篇量级、要求离线不出网、愿意为「一个词一句话都能搜到」投入调优的人。

---

## 1. 三链路：为什么一路不够

只用一个检索方法，总有它覆盖不到的查询。这里的做法是**三路并行召回，再融合**：

| 链路 | 解决什么 | 天然弱点 |
|---|---|---|
| **FTS5 关键词**（SQLite 内置，jieba 预分词） | 精确词命中、专有名词、代码标识符 | 换个说法就搜不到（同义词、口语化） |
| **稠密向量**（BGE-small-zh，512 维） | 语义相近、换个说法也能找到 | 精确匹配弱；短查询容易漂 |
| **字级 trigram 保底** | 分词器切不出来的词：生僻字、缩写、错别字 | 噪声大，单独用精度很低 |

**为什么必须有字级保底**：中文分词一定会漏。专业缩写、生僻字、OCR 错字，jieba 切不出来就整条召回不到。字级索引保证「**这个字出现过就有机会命中**」——这条直接对应需求里那句「一个字一句话都要搜得到」。

**为什么不用向量库**：几千篇的规模，SQLite 单文件 + FTS5 就能做到毫秒级，且**可解释**（能直接打开库看每张表）。引入向量数据库是为了解决分布式、多租户、水平扩展——那是另一个量级的问题。

## 2. 融合：RRF 与那个被抄错的参数

三路的分数量纲完全不同：BM25 是负值、余弦相似度是 0~1、trigram 是计数值。**直接加权毫无意义**。

所以用 **RRF（Reciprocal Rank Fusion）** —— 只按**名次**融合，不碰分数：

```
score(d) = Σ_i  weight_i / (k + rank_i)
```

### 关键发现：k=60 在小语料上是错的

网上教程几乎都写 `k=60`。那是 RRF 原论文（Cormack et al., 2009）在 **TREC 百万级新闻/网页语料**上定的。

`k` 的作用是**压平名次差距**。k 越大，压得越平：

| k | 排第 8 名得分 | 排第 80 名得分 | 差距 |
|---|---|---|---|
| 60 | 1/(60+8) = 0.0147 | 1/(60+80) = 0.0071 | 2.1 倍 |
| 2 | 1/(2+8) = 0.100 | 1/(2+80) = 0.0122 | 8.2 倍 |

后果很具体：**等权融合会惩罚「单路强命中」**。

- 一条在**单路**排第 8 的文档：`1/(60+8) = 0.0147`
- 一条在**三路都排第 80** 的噪声：`3 × 1/(60+80) = 0.0214`

**噪声赢了。** 因为它在三路都有名次，而强命中的那条只有一路。

### 实测扫参

在 100 条人工标注查询上扫 k（关精排，同一份索引）：

| k | Recall@5 | Recall@20 | MRR@10 |
|---|---|---|---|
| 1 | **90.0%** | 96.0% | 0.7215 |
| **2** | 89.0% | **97.0%** | **0.7380** |
| 20 | 85.0% | 96.0% | 0.7069 |
| 60（旧默认） | 82.0% | 96.0% | 0.7023 |

**取 k=2 而不是 k=1**（虽然 k=1 的 R@5 更高 1pp）：
1. k=1 的 MRR（0.7215 < 0.7380）和 R@20（96% < 97%）都更低；
2. `1/(1+rank)` 的权重过于极端（第 1 名 0.5 vs 第 2 名 0.333），在 100 条集上有过拟合风险；
3. k=2 与 Qdrant 官方调优文章给出的先验值一致（单答案型语料最佳 k=2~5），**外部与本地数据指向同一点**。

> ⚠️ **口径陷阱**：Qdrant 的文章用 0-based，它的 `k=61` 才等于本文口径的 `k=60`。跨来源对比时必须先对齐这个。

### 怎么验证的

```bash
# 同一进程内切档，避免模型重复加载
for k in 1 2 5 20 60; do
  KB_RRF_K=$k python judged-eval-runner.py --tag "rrfk$k" --no-rerank
done
```

🔴 **必须先验一件事**：如果 k 是「模块导入时绑定的常量」，那么改环境变量对已导入的进程无效——**五档会跑出完全相同的数**，白测一整轮。所以实现上要做成**调用时解析**：

```python
def rrf_k() -> int:
    """运行时读环境变量，缺省取默认值。
    不能写成 RRF_K = 60 然后让下游 import 它 —— 那是导入时绑定。"""
    raw = os.environ.get("KB_RRF_K", "").strip()
    return int(raw) if raw.isdigit() and int(raw) > 0 else RRF_K_DEFAULT
```

## 3. 精排：一次「加了反而更差」的优化

这一节是本文最值得看的部分——因为它是一次**失败的优化**，而失败的原因不在模型，在输入。

### 3.1 现象

给融合结果加一层 Cross-Encoder 精排（BGE-reranker-v2-m3），预期是提升排序质量。实测：

| 配置 | Recall@5 | MRR@10 | 延迟（100 条） |
|---|---|---|---|
| 关精排 | **88.0%** | **0.7235** | 快 |
| 开精排 | 76.0% | 0.5552 | 慢 22% |

**加了精排，反而掉 12 个点，还更慢。**

### 3.2 归因：不是模型不行，是喂错了东西

查具体案例：6 条问题查询里，**标准答案的得分是 0.0000 / 0.0002 / 0.0001 / 0.0011**，而排在它前面的错误答案得分是 **0.9936 / 0.7787**。

不是「没把握」，是**自信地认错人**。

顺着查输入，找到了根因：

```
Cross-Encoder 的输入取值链：chunk_text → summary → title
但三路召回的返回体都不带正文 → 只能回落到 summary（文档前 120 字）
```

**摘要里没有答案，模型当然给低分。** 而且 12/12 的错排 top1 都是标准答案的「兄弟文档」（同项目、同系列），说明模型在摘要上完全无法区分它们。

### 3.3 修复：喂命中块原文 + 滑窗

参考两个开源实现的做法（都是**喂完整 chunk 原文，不用摘要**）：

- **RAGFlow**（92k★）的注释写得很直白：
  > Feed the reranker the natural chunk text, **not the tokenized content_ltks**.
  > Neural rerankers score stemmed / accent-split tokens far lower, which **collapses relevance scores**.

- **QAnything**（14k★）的父子 chunk 做法：长块**不硬截断**，而是**滑窗（overlap=80 token）+ 每段打分取 max**。它的纯 CPU 配置也是 `max_length=512`。

🔴 **这里有个反直觉的点**：一开始我以为是「窗口太小」，想放宽到 8192。**错了。**
`sigmoid` 之后的绝对分是**全局校准**的——喂真实正文后，**所有条目**的分数一起上移，不是此消彼长。所以「标准答案上去了，错误答案就该下来」这个判断是错的。正确做法是**保持 512 + 滑窗取 max**，而不是放大窗口（放到 8192 会让 CPU 推理慢 16 倍）。

### 3.4 修复后：有效，但还是不划算

| 指标 | 修前（喂摘要） | 修后（喂正文 + 滑窗） |
|---|---|---|
| Recall@5 | 68.0% | **76.0%** |
| **低置信降级条数** | **32 条** | **1 条** |

**「降级条数 32 → 1」比 +8pp 更能说明问题**：修前有 32 条查询的池内最高分低于阈值（模型给不出分，只能降级返回原序），修后只剩 1 条——**分数重新有区分度了**。诊断是对的。

但**修完仍是 76.0% vs 关精排 88.0%**，差 12pp。所以最终：

> **代码全部保留，默认关闭。** 改一行配置即可开启做对照。

### 3.5 这件事的结论

1. **精排不是万能药。** 输入质量不行时，加一层精排是负收益。
2. **聚合指标会掩盖意图正确的修复。** 如果只看 R@5，76% 仍然低于 88%，会误判成「修了没用」；但「降级 32→1」说明修复本身是成功的，只是**没跨过收益线**。
3. **判据必须绑在基线上。** 我在这里踩过一个坑：改完 k 默认值后，还留着「R@5 ≥ 82% 才值得留精排」这条判据——而 k 变了之后关精排已经是 88%，门槛静默低了 7pp。**基线一变，所有以它为门槛的判据都要重算。**

## 4. 评测方法：怎么证明它是对的

没有评测集的优化都是凭感觉。这套方法不复杂，但必须做。

### 4.1 最小可用的评测集

- **100 条查询**，人工标注每条的标准答案（文档路径级别即可）。
- 查询要覆盖真实使用场景：口语化短查询、专有名词、换个说法、跨文档综合。
- **标注的人必须是你自己**——你需要知道「搜出来这条算不算对」。

### 4.2 三个指标

| 指标 | 含义 | 为什么用 |
|---|---|---|
| **Recall@5** | 前 5 条里有标准答案的比例 | 最贴近真实体感（人只看前几条） |
| **Recall@20** | 放宽到前 20 条 | 看「有没有捞到」，区分「没召回」和「召回但排错」 |
| **MRR@10** | 标准答案倒数排名的均值 | 衡量「排得多前」，对首位敏感 |

**Recall@20 与 Recall@5 的差值很有用**：差得大说明**排序问题**（捞到了没排好），差得小说明**召回问题**（根本捞不到）——两者的修法完全不同。

### 4.3 一次改动怎么才算「有效」

**必须做 A/B，同一份索引、同一份评测集、只改一个变量。**

```
改前跑一次 → 改后跑一次 → 对比
```

🔴 **还有一条：做零假设检验。**
看到数字变了，先别急着编原因——**同一配置重跑一次，看差值是不是 0**。我踩过这个坑：曾经把一个指标变化归因成 A，重跑发现根本没变，是读错了。

### 4.4 保留制品

每次评测都要落盘：指标、逐条结果、**代码与索引的指纹**（文件 mtime、库里的文档数/切片数、向量构建时间）。

> 为什么必须要指纹：我遇到过一次，两次评测数字对不上，最后发现是**中间索引重建过**（文档数从 4,044 涨到 4,152）。没有指纹就永远说不清「是代码变了还是数据变了」。

## 5. 工程化：让它不只是一个脚本

检索层最容易死在三件事上：**并发写坏库、备份不可用、改了不知道有没有退化**。

### 5.1 并发写锁（这条是真事故换来的）

多个自动化任务同时跑索引构建，其中一个走的是旧入口、没有所有权边界——**它把一半索引清空了自己又建不了**，几千篇只剩几百篇。而且**是静默发生的**，不报错。

修法是四层：
1. **所有权边界**：每个索引器只能写自己负责的品类；
2. **状态自愈**：库里的数量和状态文件对不上就强制重建；
3. **调用方收敛**：只留一个安全入口，其余路径全部切过去；
4. **互斥锁**：拿不到锁就排队或跳过，绝不静默并发。

### 5.2 备份要有健康闸门

「有备份」比「没备份」更危险——如果备份本身是残的。

备份前校验：文档数、切片数、向量数任何一个为 0 或明显偏低，**直接拒写并告警**；事后还要校验落盘文件的完整性。轮转按**份**算，不按文件数算（一个 SQLite 库有 `.db` / `-wal` / `-shm` 三个文件，按文件数算会把该留的删掉——这也是真事故）。

### 5.3 回归测试要「一条命令跑完」

测试散在各处、没有统一入口，等于没有测试。做法：

```
一条命令 → 跑全部套件 → 输出通过/失败 + 断言数 + 耗时 → 生成可视化看板
```

每个套件守一个**真出过事**的机制，不是凑数：

| 套件守什么 | 起因 |
|---|---|
| 并发写锁 | 见 5.1 |
| 备份轮转 | 见 5.2 |
| 构建队列 | 状态机流转 + 并发安全 |
| 元数据过滤 | 时间/路径过滤的边界条件 |
| 隐私门禁 | 私密路径必须被拒 |
| 精排降级 | 低分不能清空结果 |
| 遍历等价性 | 优化遍历后结果必须逐条一致 |

## 6. 踩过的坑（精选）

1. **中文标题从来没进过索引。**
   FTS5 用 `unicode61` 分词，汉字被归为 Unicode L*，整串中文标题被切成**一个 token**。所以「标题加权」一直是空转——`title:"知识"` 命中 **0 篇**，而正文字段命中 484 篇。
   **修法**：不改 tokenizer，**改写入侧**——标题用和正文同一套分词器切好再写进去。这个思路来自一个中文开源项目（AstrBot），它也是保持 `unicode61` 默认、靠预分词写入。

2. **`tokenize='trigram'` 看起来能解决中文，但不能。**
   它确实支持中文子串，但**查询词少于 3 个字符就不命中**——「知识」正好 2 个字。所以中文还是得走分词。

3. **注释和代码不一致，比没有注释更危险。**
   文件头注释写着「刻意不追 reports 目录」，但排除列表里根本没有 `reports`——于是日志和产物被当成代码改动，每天误报。**照注释判断行为，必踩坑。**

4. **别让「文件名差一个字母」吃掉几十 GB。**
   快照排除列表写的是 `env`，而实际目录叫 `envs`（差一个 s）。实测一个模块因此要把 **22GB / 37,767 个文件**打进快照。**这类错误不会被任何测试发现，只能靠 dry-run 看体积。**

5. **诊断前先核对输入。**
   排查「抓不到 / 无效」之前，先逐字回读原始输入（URL、ID、路径）。我曾把链接 ID 手抄错一个字母，整轮诊断都在查一个不存在的对象。

## 7. 适用范围与局限

**适用**：个人或小团队、几千篇文档、要求离线、愿意为检索质量投入调优。

**不适用 / 已知短板**：
- **数据量**：4 千篇是个人级，企业级百万级需要换后端（分布式、权限、运维那一层）
- **无多用户/权限体系**：个人工具，没有租户隔离
- **单机 CPU**：延迟靠取舍（关精排就是为了这个）
- **无 CI**：目前是本地一条命令跑测试，没接 GitHub Actions
- **没算覆盖率**：走的是「关键路径 + 真事故回归」，不是全量覆盖

**如果数据量上 10 倍，顺序应该是**：① 先扩评测集到 300~1000 条（否则无法判断改动好坏）② 再换检索后端（但保留 RRF 这一层，它不绑定后端）③ 最后重新评估精排（数据量变了，收益曲线会变）。
**顺序不能反：先有度量，再换架构。**

---

## 8. 一句话总结

**检索的瓶颈通常在「捞得对不对」，不在「生成得好不好」；而证明「捞得对不对」的唯一办法，是先有一份自己标的评测集。**

所有优化都应该能回答一个问题：**这次改完，是涨了还是跌了，涨跌多少。**
答不出来，就还没到优化的阶段。
