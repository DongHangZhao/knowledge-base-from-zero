# 版本发展史（v1.0.0 → 最新）

**简体中文** ｜ [English](version-history.en.md)

> 这份文档回答一个问题：**这个项目是怎么一步步长成现在这样的。**
> 不是发版清单，是发展记录 —— 包括走通过的路、被否决的方案、以及试了才知道不行的实验。
>
> 数据来源全部可追溯：`git tag`、`gh release list`、根 `CHANGELOG.md`、
> [`modules/知识库索引/CHANGELOG.md`](../modules/知识库索引/CHANGELOG.md)（引擎线 49 段实测记录）。
> 两份日志的分工：**根日志记仓库级里程碑**，**引擎日志记每一处改动的实测数字与失败结论**。

## 三、阶段 1 · 门户开源（2026-10-21 ~ 10-27）

仓库在这里诞生。目标不是「放代码」，是**把知识库该怎么做这件事讲清楚**。

| 版本 | 日期 | 这一步做了什么 |
|---|---|---|
| v1.0.0 | 10-21 | 首个版本：门户 9 页签 + 模板 + 文档 |
| v1.1.0 | 10-21 | 许可 MIT → **KBL-1.0**（禁商用 + 强制署名 + 相同方式共享）；全量脱敏；隐私扫描工具上线 |
| v1.2.0 | 10-21 | 全量中英双语（README / RELEASE / 9 篇 docs / 6 份模板 / 门户文案） |
| **v1.3.0** | 10-22 | 门户新增 **🔍 全库检索** 页签（三链路 RAG + `/api/rag` + 带引用的上下文包）；界面中英一键切换 |
| **v1.3.1** | 10-22 | **rerank 精排层**：Hybrid → RRF → rerank → top-k；短查询自动跳过保字面灵敏度；零命中显示警示条 |
| **v1.4.0** | 10-27 | 《检索层设计与评测方法》+《使用指南》中英双语 —— 从「给你代码」变成「教你怎么设计和评测」 |

**这一阶段的三个决定一直影响到今天：**
1. **许可用 KBL-1.0 而不是 MIT** —— 可以随便用、随便改，但不可商用、必须署名。
2. **中英双语不是加分项，是交付标准** —— 每篇文档顶部都有互链，两版一一对应，有专门的双语校验脚本。
3. **只给代码不给方法等于没交付** —— v1.4.0 起，方法论文档和代码是平级的交付物。

## 四、阶段 2 · 引擎成型（2026-10-23 ~ 11-03）

这段是引擎内部线，解决了「真库里什么都有的情况下还能不能搜出来」。

**能不能吃下真实的库（v1.11.0 ~ v1.13.39）：**

- `v1.11.0` 元数据过滤（`--since` / `--path-prefix`）
- `v1.13.21` ~ `v1.13.23` **`.doc` 老格式纳管** —— 此前 622 篇 Word 老文档全部搜不到
- `v1.13.32` ~ `v1.13.36` **多模态落地**：图片 OCR（2,448 篇）、音视频转写（272 篇）、扫描件 PDF（580 份 / 5,101 页，提取快 5.74 倍）
- `v1.13.38` 修掉一个**会「静默丢账」**的缺陷：扫描件处理失败不报错，账面上看着都成功了
- `v1.13.39` **隐私出口门禁**：本机可检索，出口必须过门禁 —— 检索层不加限制，只加出口

**检索质量到底靠什么（v1.13.x 的一串实测）：**

| 改动 | 结论 |
|---|---|
| `v1.13.7` RRF 融合常数 **k 60 → 2** | R@5 **+7pp**（@旧索引）；重建索引后复核只有 **+3pp**，`v1.13.9` 专门做了一次口径纠错 |
| `v1.13.8` 精排输入从「文档摘要」换成「命中块正文 + 滑窗取 max」 | 降级 32 → 1 |
| `v1.13.10` 别名/同义词表（查询时扩展，零重编码） | 中英术语错配被补上 |
| `v1.13.18` 分块 overlap 立项调查 | **沙盘否决，不做** —— 没有正收益 |
| `v1.13.20` 换 embedding 模型（S4） | **实测否决** |
| `v1.13.20` 缩小块（S4c） | **沙盘否决** —— 两条路都走死了 |
| `v1.13.28` 向量路块级过采样 | **零收益**，做成可配但默认保持历史行为 |

**结构改造与工程化（v1.14.x）：**

- `v1.14.0` **分块结构改造上线**：`CHUNK_MAX 1200 → 480` + 断句吸附，片段完整性覆盖率 **5.6% → 76.4%**；语言路由（m3 多语塔，默认关）
- `v1.14.1` rerank 精排层 GPU 化（`device=auto` + fp16，`KB_RERANK_DEVICE=cpu` 可回退）
- **`v1.14.2`（2026-11-03）引擎并入开源仓库** —— 这是仓库线的关键节点：全机路径脱敏后公开，同一版做重复块治理（垃圾块 3.43% → 1.67%，全量重切 116,150 → 111,228 块），并补上首次离线 CI

**这一阶段最值钱的不是做了什么，是否决了什么。** 六条被否决的方案每一条都有实测数字，
写在这里是为了下次别再试一遍。

## 五、阶段 3 · 可验证（2026-11-04 ~ 11-11）

主题从「做得更好」转向「**凭什么说更好**」。

**v1.15.0（11-04）一次把「能跑」变成「能验」：**

- T01 测试止血 + 首次离线 CI；T02 增量闭环（m3 随 build 补 + 四表一致性断言）
- T03 查询改写三层；T04 产品化三件套（人设配置 / 双许可说明 / tag 驱动发版）；T05 图谱 1pt 实验脚手架
- 新增 MCP 服务暴露（零依赖 stdio）+ 正式评测 harness 抽离（`metrics.py` + `eval_rag.py`）
- 🔴 **`#41` 图谱 1pt 实验实测 FAIL，归档不做** —— 判据开工前就写死，没达标就是没达标
- 🔴 **查询改写 L0 实测否决，默认回滚 off** —— 延迟涨，逐题 diff 只救回 0 条、弄坏 1 条
- 🔴 **发现评测污染**：`eval_rag` 对生产库不是只读的，会往 `query_log` 写行，93% 是评测题

**v1.16.0（11-04）** 清掉 93% 的评测污染 + 图谱实验归档 + 领域词典抽取。
一句话决策理由：**评测集被污染时，任何分数都不具备决策效力，先清数据再谈指标。**

**v1.17.0 / v1.17.1（11-09）** 独立知识图谱子系统 v1.0.0 → v1.0.1：脱敏、可复算、带交付闸门；
订正一个「沙盒一删，评测段整段不打印」的闸门口径 —— 门禁宁可 fail loud，也不能静默少打印一段。

**v1.18.0（11-11）** LLM 能力层工程化：入口零引用守卫、边质检、冻结人标题集的配对改写 A/B
（McNemar 精确 p + 延迟增量 + 快照守卫）、报表、429 压测、断点续跑，外加一个
「生产模块 → 本仓」的可复跑镜像脚本（`--check` 幂等），替代手工复制 28 个文件。

## 六、阶段 4 · 发布工程（2026-11-17 ~ 11-19）

主题：**别人能不能真正拿到、跑起来。**

| 版本 | 日期 | 这一步做了什么 |
|---|---|---|
| v1.19.0 | 11-17 | 双库收敛（生产侧修复回流）+ 署名统一 + `outputs/` 脱敏排除；修 C7 门禁假红（`use_cache` 未同步导致 selftest 8/1） |
| **v1.20.0** | 11-17 | **多平台发布产物**：源码 zip + Windows exe + Linux + macOS + Android apk；新增 `kb-hub/android/` 子项目（p4a webview bootstrap）。此前 v1.3~v1.19 的所有 Release **只有 GitHub 自动生成的 Source code，没有任何二进制** |
| v1.21.0 | 11-19 | rerank 切 ONNX 推理（CPU 冷启动 23.8s → 20.4s、稳态 1.31x，排序 3/3 一致）+ 查询级缓存（默认 off）+ ONNX 导出脚本落库 |
| v1.22.0 | 11-19 | **容器化部署**：`Dockerfile`（非 root / `WITH_VECTOR` 开关）+ `docker-compose.yml`（回环绑定、模型只读挂载、只读根文件系统）+ 构建上下文隐私门禁 |
| v1.22.1 | 11-19 | 修容器映射端口下页面 `Failed to fetch`：API 改同源地址 + `no-store` |

**这一阶段的坑最有代表性：v1.20.0 之前十几版 Release 全是「空的」** ——
`gh release create` 返回 0、页面上有 Source code、CI 全绿，但没有一个可下载的二进制。
这个坑一直留到阶段 5 才被彻底机制化解决。

## 七、阶段 5 · 召回侧与机制化（2026-11-20）

| 版本 | 这一步做了什么 |
|---|---|
| **v1.23.0** | **召回侧「文档侧问句」通道**（doc2query）：离线给每篇文档补「用户可能会怎么问」的索引，独立库、不重跑 build、不抢 build.lock；检索侧 FTS5 + 向量双路 RRF 融合，接在 HyDE 之后、元数据过滤之前。实测正确文档进池 **51 → 70（+19.39pp）**、零误伤、延迟 +19ms。同版否决「标题规则问句」（独立集 top1 40 → 35、MRR −0.20）：**并表 ≠ 加权** |
| **v1.23.1** | **发版机制修复**：`release.yml` 重写为「构建 → 上传 → 自检」一体，构建失败就不建 Release；新增资产门禁 `tools/release_assets_gate.py`；`publish_to_github.bat` 收敛为只 push 不发版 |
| v1.23.2 | 资产门禁体积下限 200 KB → 100 KB（老版本源码包本来就小，不该判红） |
| v1.23.3 | 删除 v1.3.0~v1.19.0 九个 Release 上**误挂的 apk**：那些 tag 的源码里没有 `kb-hub/android/`，本就没有 Android 版 |

**v1.23.1 的根因值得单独记一笔：** 资产漏发不是「忘了」，是四个环节同时缺位 ——
`release.yml` 一个 asset 参数都没有、注释把「人工上传」写成有意设计、人工上传没有任何载体、
11-17 那次补齐只是一次性动作。**凡是「每次都要做」的事，必须落在流水线里，不能落在记忆里。**

## 附录 D · 三个反复出现的教训

1. **「跑通了」不等于「验证了」。** `gh release create` 返回 0、CI 全绿、页面有 Source code，
   三件事都不代表资产挂上去了 —— 判据只能是去数文件。
2. **默认值不能靠感觉设。** L0 查询改写、`#41` 图谱都是先设了默认，后被实测打回来。
   现在的规矩：**判据在开工前写死，没达标就是没达标。**
3. **一次性人工补齐不等于机制。** 11-17 把 10 个历史 Release 的资产补得很全，
   但下一版照旧漏 —— 因为那个动作不在流水线里。现在发版 = 构建 + 上传 + 自检，一体。
