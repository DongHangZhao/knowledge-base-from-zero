## 0. 为什么不能用单跳集测 1-hop

单跳题的 gt 只有一篇，答案就在那一篇里。给这类题加 1-hop 邻居，**邻居全是噪声**：
既提不了 Recall（gt 本来就排得到），又必然拉高延迟。1-hop 的价值只在多跳：
**答案分散在两三篇文档里，单路召回只能捞到其中一篇**。

## 1. `hops` 字段的语义

`hops = len(gt)` = **回答这条 query 需要读几篇文档**。

- `hops: 2` → 22 条
- `hops: 3` → 8 条

## 2. 锚点规则（第一版曾把锚点也禁掉，导致 1-hop 全程返回空）

`kg_gate.expand_1hop` 的机制是 `_query_entities(query)` → 查侧表里共享这些实体的 chunk。
**查询里没有实体，这一路直接返回 `[]`** —— 于是 treat 组测的是「没东西可扩」而不是「图谱没用」，
那是假阴性，比不做实验更糟（会得出一个看起来有数据支撑的错误结论）。

第一版为了防关键词作弊，把「gt 文件名原词」全禁了，连**锚点**一起禁掉，题面变成
「那批系统里第一个上线的那套…」这种没人这么说话的句子。现行规则两句话：

1. ✅ **第一跳的锚点实体必须出现**（系统名 / 主题名 / 上级概念）—— 这是用户已知信息，不是答案。
   第一跳的信息本来就该在提问里，图谱做的正是「第一跳 → 第二跳」这段连接。
2. ❌ **最终答案所在文档的标题、以及答案本身的关键词不许出现。**

锚点加回来之后，首篇（枢纽文档）会被关键词路轻松命中 —— **这没关系，它就是第一跳**。
题目的难点在第二跳：得从枢纽跳到子文档才算真命中，所以每条的 gt 都保留了首篇。

额外加了一条比 team-lead 要求更严的自检：**至少一个锚点必须出现在 gt 末篇正文里**。
理由：1-hop 是「查询实体 → 共享该实体的 chunk」，若答案 chunk 里根本没有这个实体，
1-hop 扩不过去，这条题对 treat 组仍然是零贡献 —— 那样锚点就只是装饰。
