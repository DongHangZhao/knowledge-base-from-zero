# ADR-2026-11-20 · 召回侧补一路「文档侧问句」通道

> **状态**：已落地（生产侧默认开、一键可关）· 已发版 v1.23.0
> **许可**：KBL-1.0（不可商用 · 强制署名 · 相同方式共享），署名 FallenPetal
> **本文不含真实姓名、学号、公司名、真实项目名、本机绝对路径。**

---

## 0. 一句话结论

**失败题里将近一半是「答案就在库里、但压根没进候选池」，精排够不着——这类问题只能靠召回侧扩充解决。
方向选「文档侧生成问句」（doc2query），不选「查询侧扩词」：后者依赖以查询文本为键的离线缓存，
新查询必然未命中，测出来的收益是假的。**

---

## 1. 背景：为什么不再优化「检索前判别」

此前三条路都试过，方向一致但均不显著：

| 尝试 | 做法 | 结果 |
|---|---|---|
| 查询改写 | 规则拆句 / 同义词扩展 | 提升有限，显著性不足 |
| 查询分流 | 按问句类型选不同召回策略 | 不显著 |
| 检索前分类器 | 判断「这道题该走哪条路」 | 不显著 |

真正的卡点在**候选池**：把失败题逐条归因后发现，其中约 46%~47% 的正确答案文档
**从未出现在前 100 名里**。精排只在前 100 名里挑，够不着池外的东西——分流再聪明也白搭。

所以换方向：**不动查询，动文档侧**。

---

## 2. 决策一：加「文档侧问句」通道（采用）

### 做法

离线给每篇文档生成 3 条「普通用户会怎么问」的问句，存进**独立** sqlite：

```
state/kb_questions.db
  questions(id, doc_path, doc_title, question, src, ts)
  qfts(seg, question, doc_path)      -- FTS5，jieba 分词后入库
  qvec(qid, dim, vec)                -- bge-small-zh CLS 向量
```

检索时多一路召回：查询 → FTS5 命中问句 → 映射回文档 + 向量余弦 → 两路 RRF → 与既有三链路再 RRF。

**为什么落独立库而不是写进主库**：问句是派生数据。写进主库就得重跑 build、抢 build.lock，
还会与并发写入打架。独立库随时可删可重建，零侵入。

**为什么接入点选在「精排前、元数据过滤前」**：此时融合池已完整（各路召回都跑完），
且这一路新增的文档同样会经过 `--since / --path-prefix / --category` 过滤——
放在过滤之后就会绕过契约，给出本该被过滤掉的旧文档。

### 实测

私有库规模：约 1.1 万篇文档 / 17.5 万块 / 98 条评测题（该桶 51 条原本进不了池）。

| 指标 | 关 | 开 | 变化 |
|---|---|---|---|
| 正确文档进池（top-100） | 51 | **70** | **+19.39pp**，McNemar b=0，p=3.8e-6 |
| 延迟（中位） | 0.449s | 0.468s | **+19ms** |
| 独立集 top1（71 条新题） | 40 | 42 | p=0.82，方向正、未达显著 |
| 独立集 MRR@10 | 0.675 | 0.687 | +0.013，95%CI 跨 0 |

**b=0 的含义**：原本能进池的文档，一个都没掉出去——这是零误伤的直接证据。

### 为什么「设计集显著、独立集不显著」还要上

不是机制无效，是**独立集检验力不足**：独立集 71 条里只有 7 条原本在池外，
top1 只有 31 格可动；而设计集有 47 格。用 7 格尺子量不出 19pp 的差别。

但它能证明两件更重要的事：**方向一致（两集都为正）+ 零误伤**。
所以决策是「默认开 + 一键关」，**不声称显著有效**，并把独立集指标原样写在 CHANGELOG 里。

## 3. 决策二：不采用「标题规则问句」（否决）

顺手试过一条零成本路：把文档里所有 `#` 标题抽出来，每条拼成一个问句（4.5 万条 / 1.1 万篇，5 秒建完，0 token）。

| 指标 | 基线 | 加标题库 |
|---|---|---|
| 设计集进池 | 51 | 60（+9.18pp，看着很好） |
| **独立集 top1** | **40** | **35**（p=0.0013） |
| **独立集 MRR@10** | **0.675** | **0.473**（−0.202） |

**为什么看起来涨、实际是伤**：4.5 万条里大量是「目录 / 总结 / 概述 / 参考文献」这类标题，
它们对**任何**查询都有字面重合。等权 RRF 下一条 1/(60+1) 的分数，
就能盖过主链路排第 60 名的真命中。

**并表 ≠ 加权。** 把低质大库等权并进融合，进池会涨、top1 会掉——这是典型的「指标好看、体验变差」。

降权到 0.15 / 0.3 仍然伤。故整条路放弃，只留作反例。

## 4. 决策三：以查询文本为键的离线缓存，其 Δ 不得进交付口径

这是本轮最重要的一条方法学结论，起因是一次「数字太漂亮」的自我怀疑。

某查询扩词机制在回放集上测出 **+26.53pp**，独立另一机制测出 **+13.27pp**。读代码才发现：

```python
def expand_llm(q):
    hit = cache.get(q)          # 缓存键 = 查询文本
    if hit is None:
        return []               # 未命中直接回退，不现场调模型
    return hit
```

缓存是**照着这批评测题**生成的，所以回放集命中 96/98、67/98；换一批没见过的查询，
命中率为 **0**——机制根本没生效。

**判据**：任何机制，先跑一遍**没见过的新样本**。命中率不成立，就把 Δ 标红，不进交付口径。
同理，**「独立集已经饱和」就没有资格当判决**：基线 90% 都进池时，
进池率只剩个位数格子，这时只能证「不伤」，不能证「有效」。

## 5. 边界与未做（不粉饰）

- **覆盖边界**：只覆盖生成过问句的文档。未覆盖的文档此通道不贡献分数——
  不是「全库都变好了」。
- **媒体页跳过**：图片 OCR / 音视频转写页故意不生成问句，因为会产出「图里写了什么」
  这类无区分度问句，实测拉低体验。
- **未做**：精排开启下的全量 A/B（本文数据均为关闭精排的召回层指标）；
  词表误伤的逐条抽检；用本地小模型替代远程生成。
- **成本**：离线生成消耗 token（一次性）；在线检索 **0 次模型调用**。

## 6. 复现

```bash
# 1) 生成问句并建库（先小样本试）
python modules/知识库索引/qch_build.py --limit 200 --workers 4

# 2) 验证通道
python modules/知识库索引/qch_channel.py "你的问题"

# 3) 关掉再对比
KB_QCH=off python modules/知识库索引/kb_rag.py search --query "你的问题" --topk 5
```

**回滚**：`KB_QCH=off` 即恢复原三链路（关时零加载、与接入前逐位一致）；
彻底清除则删 `state/kb_questions.db`。
