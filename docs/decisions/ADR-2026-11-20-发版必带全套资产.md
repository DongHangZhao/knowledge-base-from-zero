# ADR-2026-11-20 · 发版必带全套资产（Release assets 不许再靠记忆）

> **状态**：已落地（`release.yml` 重写 + 资产门禁）· 已补发 v1.21.0~v1.23.0
> **许可**：KBL-1.0（不可商用 · 强制署名 · 相同方式共享），署名 落花飞雪·
> **本文不含真实姓名、学号、公司名、真实项目名、本机绝对路径。**

---

## 0. 一句话结论

**GitHub 的「发版」= Release 正文 + 5 个资产（源码包 / Windows / Linux / macOS / Android）。
只发正文不挂资产 = 没发版。** 而「手工上传资产」在没有清单、没有门禁的情况下，
**必然会被漏**——v1.21.0 / v1.22.0 / v1.22.1 / v1.23.0 连续四个版本全漏，
同时 CI 全绿、CHANGELOG 还写着「已挂载全部 Release」。
修法不是「下次记得传」，而是把资产构建塞进 `release.yml`：**构建没成功就不建 Release。**

---

## 1. 事实：漏了哪些、漏得像不像成功

| 版本 | 发布日期 | 应有资产 | 实际资产 |
|---|---|---|---|
| v1.19.0 | 2026-11-17 | 5 | 5 ✓（人工批量补齐） |
| v1.20.0 | 2026-11-17 | 5 | 5 ✓（同上一次补齐动作） |
| v1.21.0 | 2026-11-18 | 5 | **0** |
| v1.22.0 | 2026-11-19 | 5 | **0** |
| v1.22.1 | 2026-11-19 | 5 | **0** |
| v1.23.0 | 2026-11-20 | 5 | **0** |

取证方式：`gh release view <tag> --json assets`，四个版本返回空数组。

**「看起来像成功」的三个假信号**（这是问题能连漏四版的原因）：

1. `gh release list` 里版本在列 → 以为发了；
2. Release 页面上有 `Source code (zip)` / `Source code (tar.gz)` 两个下载 → 以为资产在
   （这两个是 GitHub 对任意 tag 自动生成的，**和发版动作无关**）；
3. `release.yml` CI 绿 → 以为流程完整（旧工作流本来就不传资产，它绿得毫无意义）。

---

## 2. 根因链（不是「忘了」，是机制缺位）

1. **旧 `release.yml` 结构上就不传资产。** 只执行
   `gh release create "$TAG" --notes-file notes.md --verify-tag`，
   连一个 asset 参数都没有。文件头注释还明确写着
   「不附 exe：二进制是手工产物（体积大、需本机签名验证），走人工上传，CI 不碰」。
2. **「人工上传」没有任何载体。** 没写进 `release_gate.py`、没写进 `publish_to_github.bat`、
   没有 checklist、没有事后核对脚本。它只存在于「当时的上下文」里。
3. **11-17 那次「10 个历史 Release 全部补齐 assets」是一次性人工动作。**
   它被记进了 CHANGELOG 的 `[Unreleased]` 段，但**没有被固化成「每次发版都做」的步骤**。
   一次性的手工补齐，只能覆盖它执行的那一刻；下一次发版照旧漏。
4. **门禁只校验版本号，不校验资产。** `release_gate.py --check` 检查 VERSION /
   CHANGELOG / RELEASE / tag 六处口径一致——全过。于是「版本对了」被误当成「发版对了」。
5. **没有事后取证闭环。** 发完版没有人（也没有脚本）去数一次「这个 Release 到底挂了几个文件」。

一句话：**校验的是「版本号对不对」，交付的是「用户能不能下载到东西」，两者之间没有任何桥。**

---

## 3. 决策

### 3.1 `release.yml` 内联构建 + 上传（strict）

```
push v* tag
  └─ job assets:  calls build-assets.yml（reusable）
       ├─ source-zip   → kb-from-zero.zip（按当次 tag 打）
       ├─ binary       → kb-hub.exe / kb-hub-linux / kb-hub-macos（矩阵）
       └─ android-apk  → kb-hub-android.apk
  └─ job release: needs: [assets]
       ├─ release_gate --check --tag（版本六处口径）
       ├─ privacy_scan --git-only --no-assets（L1+L3）
       ├─ make_release_notes（CHANGELOG 无该版本段 → 失败）
       ├─ download-artifact（asset-* 合并）
       ├─ 清点 5 个文件名（缺一个就 exit 1）
       ├─ gh release create ... 5 个资产
       └─ release_assets_gate --tag（回查资产真的挂上了才收口）
```

**为什么 strict（构建失败就不建 Release）**：残缺 Release 比没有 Release 更糟——
用户看到版本存在但下不到东西，而维护者以为发过了。宁可红着不发，也不要静默半成品。

**为什么不沿用「CI 只构建、人工上传」**：那正是本次事故的机制本身。
隐私方面的顾虑用 `privacy_scan --git-only --no-assets` 在 CI 内兜 L1+L3 解决；
本地带词表的深度扫描仍是发版前必做项（写在 HANDOFF），但**不再作为「上传」的前置阻塞**——
因为阻塞点一旦落在人的记忆上，就会漏。

### 3.2 新增 `tools/release_assets_gate.py`

只读核对：`--tag V` / `--all`，按名核 5 个资产 + 体积下限，缺任一 rc=1。
既做 CI 收口自检，也做历史体检（本次就是靠它一次性看清 4 个版本全空）。

### 3.3 `make_release_zip.py` 支持 `--ref`

补历史版本时，源码包必须来自**该 tag 的 git 对象**，不能拿当前工作区打一份挂上去
（那等于把新代码冒充成老版本）。实现上直接 `git cat-file blob` 读内容，工作区零改动。

两个附带修复（都是补发时踩出来的）：

- **中文路径静默丢失**：`git ls-tree` 默认 `core.quotepath=true`，把 `modules/知识库索引/`
  输出成八进制转义字符串，按扩展名过滤时整棵中文目录被丢掉——v1.21.0 首打只收到 69 个文件
  （正确应为 203）。必须 `-c core.quotepath=false`。
- **VERSION / Dockerfile 从没进过发布包**：白名单只认 `LICENSE/NOTICE/.gitignore`，
  两个无扩展名文件一直被过滤。用户解压后既不知道版本、也没法 `docker build`。

再加 `_versions/` 到排除目录：它是本地发版快照，里面的 `.md` 正好在白名单里，
不排除会被打进公开包（含真实评测数据的风险）。

## 4. 取证

| 项 | 证据 |
|---|---|
| 漏发范围 | `gh release view v1.21.0/v1.22.0/v1.22.1/v1.23.0 --json assets` → 全空 |
| 门禁有效性 | `python tools/release_assets_gate.py --all` → 修复前 `ASSETS=FAIL 4/4`，rc=1 |
| 源码包版本对应 | 4 个 zip 解出的 `VERSION` 分别等于 1.21.0 / 1.22.0 / 1.22.1 / 1.23.0 |
| 中文路径 | v1.21.0 包内 134 条中文路径文件（修复前 0 条） |
| 补发后 | `release_assets_gate.py --all` → `ASSETS=PASS`，rc=0 |

## 5. 边界（未做 / 不承诺）

- **不承诺「CI 一绿就等于可对外发布」**：CI 隐私门只有 L1+L3，本地词表深度扫描仍要人跑一次。
- **不承诺二进制跨版本逐位一致**：每次发版重新构建，sha 会变；`--sha-same` 未实现（不需要）。
- **Android 构建链仍依赖外网**（p4a / NDK / SDK 下载），失败则整次发版不发。
  这是有意的：构建链坏了应当先修构建链，而不是降级成「先发 4 个」。
- **过往 v1.20.0 及更早版本的资产未重新构建**，沿用 11-17 那次人工补齐的产物。

---

## 6. 以后如何防止复发

1. `release.yml` 的 strict 结构（构建失败 → 无 Release）；
2. `release_assets_gate.py` 作为 CI 最后一步 + 本地随时可查；
3. **「发版完成」的判据写死为**：`release_assets_gate --tag <tag>` 返回 0，而不是
   「`gh release create` 返回 0」——后者只代表 API 收下了请求。
