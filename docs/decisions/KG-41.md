# #41 知识图谱 1pt 实验 · 决策记录

> 状态：**FAIL，归档，不进生产**
> 判据**开工前写死**：`all@5` ≥ +3.0pp **且** p95 ≤ +150ms
> 三轮实验（v1 抽取碎片 / v2 词性过滤 / v3 领域词典）全部为负收益
> 完整数据与复跑方式：`modules/知识库索引/experiments/kg41-图谱召回/README.md`

## 一、结论

**1-hop 共现扩展在 30 条多跳集上是负收益，且随权重单调恶化。**

| 版本 | 抽取方式 | baseline `all@5` | treat `all@5` | Δ |
|---|---|---|---|---|
| v1 | 分词直抽 | 50.0% | 46.7% | −3.3pp |
| v2 | + 词性 + df 过滤 | 50.0% | 46.7% | −3.3pp |
| v3 | **+ 领域词典注入**（抽取已修对） | 50.0% | 43.3% | **−6.7pp** |

图谱路权重扫描（v3 侧表）：

| `KB_W_KG` | 0.5 | 1.0 | 1.5 | 2.5 |
|---|---|---|---|---|
| treat `all@5` | 43.3% | 43.3% | 40.0% | **30.0%** |
| Δ | −6.7pp | −6.7pp | −10.0pp | **−20.0pp** |

**权重越高越差，单调恶化。** 这一条排除了「扩展结果排序不够靠前」的解释 ——
如果只是排序问题，提高权重应该翻盘；单调恶化只能说明**扩进来的内容本身是错的**，
权重越大，错的东西挤掉对的东西越多。

## 二、根因：共现 ≠ 相关

`expand_1hop` 的机制是「找出共享某实体的 chunk」。失效点在**枢纽实体**：

- 「集群五大系统」这类第一跳锚点的文档频次极高（几十篇都提它）
- 它的一跳邻居 = 半个语料库
- 扩出来的绝大多数是「提到过这个词」的文档，**不是答案所在的那一篇**
- 多跳问题的第一跳锚点，恰恰总是枢纽词 → 这个机制在它最该起作用的场景下必然失效

**量化证据**：以「集群五大系统项目」为种子做 2 跳扩展，
覆盖 **1429 个实体**（占全库 4867 个的 **29%**）、36826 条边。
「2 跳就能摸到三成实体」意味着这个起点本身不携带任何定位信息 ——
它不是"跳到了答案附近"，而是"跳到了整个知识库"。

本质差异：

| 多跳检索需要 | 共现图谱提供 |
|---|---|
| 有方向的关系（A 的 X 字段指向 B） | 无向关联（A 和 B 同段出现） |
| 有类型（依赖 / 属于 / 替代） | 无类型 |
| 可判定（查得到 / 查不到） | 只能算权重 |

**这不是调参能解决的，是表达能力的上限。**

## 三、第一版「图谱无效」的结论已被推翻并改写

v1 得出的是「图谱无效」，但复盘发现 v1 的失效点在**实体抽取**，不在图谱机制：

```
jieba.cut("集群五大系统项目里…")
  → ['集群', '五大', '系统', '项目', ...]
```

「系统」被 df 过滤（太泛），剩「集群」「五大」这种碎片去扩邻居，
实测召回的是求职简历 —— 起点就是错的，所以 v1 是**假阴性**。

v3 把抽取修对了（从 7524 篇文档标题挖领域词典注入分词器，
关键短语 5/6 整体保留，中文实体占比 7.8% → 70.5%），
**在同一份评测集上仍然负收益** —— 这时「图谱作为召回通道无效」才是可信结论。

## 四、两个方法学教训（比结论更值钱）

### 1. `any@5` 测不出多跳，差点得出「100% 完美」的假结论

多跳集每条题有 2~3 个 gt（第一跳总览 + 第二跳答案）。
原 Recall 口径是「任一 gt 命中即算 hit」，于是首轮跑出：

```
baseline any@5 = 100%    treat any@5 = 100%    Δ = 0
```

差点据此收工认定「图谱无害也无用」。**真相是 any@5 已封顶，
任何改进都不可能显现。** 换成 `all@5`（全部 gt 都要命中）后
baseline 立刻掉到 50%，问题才显形。

> **规则：多答案评测必须用全命中口径。** 任一命中口径在 gt≥2 上会饱和，
> 把真实差异全部吃掉。这条已固化成脚本 `kg_eval_both_hit.py`（双口径同出）。

### 2. 「分段测速 × 全量」是错的估算方式

全库建侧表两次超时（16 进程卡死一次、单进程 28 分钟未完一次）。
根因不是分词慢（实测 `jieba.cut` 全库只要 1.7 分钟），而是：

- 用 1000 条样本测速，线性外推到 11 万条 —— 忽略了**结果累积带来的非线性退化**
- Windows 上 multiprocessing 16 进程各载一份 jieba 词典（~600MB/进程）把内存打爆

> **规则：估算耗时必须跑到真实规模的 1/10 以上再外推；多进程先算内存账。**

## 六、第二轮：按业界方案重做（PPR 图扩散）

第一轮结论是「1-hop 无效」，但那只否定了**共现扩邻居**这一种做法。
按用户要求参考业界方案重做了一版，依据是三个开源实现：

| 项目 | 借鉴的机制 | 用到的部分 |
|---|---|---|
| **HippoRAG**（NeurIPS 2024） | PPR 替代 BFS + 节点特异性 + 实体-文档矩阵 | 全部实现 |
| **LightRAG**（EMNLP 2025） | 双层检索（local 实体 / global 主题） | 实现了 community 层，未做 LLM 摘要 |
| **Microsoft GraphRAG** | Leiden 社区检测 + 模块化摘要 | 用 Louvain 做划分（摘要需 LLM，跳过） |

### 6.1 换掉了四处，每一处都是实测逼出来的

| 改动 | 原来的做法 | 现在的做法 | 为什么换 |
|---|---|---|---|
| **扩散算法** | 1-hop BFS（走到就全收） | **PPR**（按结构分配概率，逐步泄漏） | BFS 对枢纽实体无解；PPR 的分数归一化，出边再多也摊薄 |
| **边权** | 原始共现次数 | **NPMI**（归一化点互信息） | 15684 个实体用原始共现连出 311 万条边、平均度 397，PPR 一扩散就摊平成一片 0.002 |
| **虚词剔除** | 无 | **度/df 比值 > 25 剔除** | 见 6.2，这是最关键的一条 |
| **打分** | 邻居 chunk 直接进候选池 | **按文档聚合 + 长度惩罚** | 直接 sum 会让 `wiki/log.md`（546 块）靠长度霸榜 |

### 6.2 关键发现：df 和 NPMI 都压不住虚词，只有「度/df 比值」能

实测数据（196 篇侧表）：

| 词 | df | 度数 | 度/df |
|---|---|---|---|
| 一种 | 33 | 2767 | **83.8** |
| 能够 | 26 | 2491 | **95.8** |
| 一些 | 20 | 2352 | **117.6** |
| 它们 | 39 | 2257 | **57.9** |
| 血透 | 7 | 52 | 7.4 |
| 时序 | 5 | 31 | 6.2 |
| 某集群五大系统 | 15 | 85 | 5.7 |

差一个数量级，阈值取 25 干净切开，一次剔除 1709 个虚词。

**为什么 df 判据失效**：「一种」只在 33 篇里出现，df 一点都不高；但那 33 篇里几乎每句都有它，
于是和 2767 个不同实体共现。**df 看不出问题，度数看得出。**

**为什么 NPMI 也失效**：它和几乎所有词共现时 `p_ab ≈ min(p_a, p_b)`，
PMI 恒为正，加权后照样是枢纽。

### 6.3 实验数据

| 配置 | 边数 | `all@5` | Δ | p95 | Δp95 |
|---|---|---|---|---|---|
| baseline | — | 50.0% | — | 512ms | — |
| +1hop（第一轮） | — | 46.7% | −3.3pp | 520ms | +8ms |
| **+PPR（脏图，min_w=1）** | 302 万 | 53.3% | +3.3pp | 1765ms | +1245ms |
| +PPR（脏图，min_w=2） | 70 万 | 50.0% | +0.0pp | 741ms | +228ms |
| **+PPR（干净图，min_w=2）** | 15.9 万 | **53.3%** | **+3.3pp** | 502ms | **−9ms** |
| **+PPR（干净图，min_w=3）** | 13.4 万 | **53.3%** | **+3.3pp** | 459ms | **−31ms** |

三个结论：

1. **剔除虚词同时解决了「无效」和「慢」**。脏图上 PPR 要么无效要么 +1245ms；
   干净图上参数两档都是 +3.3pp，延迟反而降了。因为图小了 4 倍，迭代本身变快。
2. **延迟不再是问题**（−9 ~ −31ms），这推翻了「图检索必然慢」的预设。
3. **但 +3.3pp 的绝对量是「1 条样本」**（30 条里多命中 1 条）。
   脏图测试时 min_w 取 1/2/3/5 呈现「+、0、+、0」交替 —— 说明那 1 条在不同参数下偶然翻动，
   **统计上不显著**。

### 6.4 一个可复现的能力改善（不是统计结论）

单条 case（mh04「第一个上线的那套用了哪种库承载时序数据」）：

```
修复前：PPR 结果第 1 名 = WorkBuddy企业微信互通（无关）
修复后：PPR 结果第 1 名 = wiki/项目/某集群五大系统-血透系统.md   ← 正是答案篇
```

机制上讲得通：查询里的「时序」和文档里的「InfluxDB / 时序」在图上通过 NPMI 强边相连，
PPR 把概率传过去。这是**真实的能力**，只是在这份 30 条集上只体现为 1 条。

### 6.5 判定

**技术上成立，统计上不显著。**

- 不建议现在就上生产（+1 条的收益不值得引入一张 8 万节点的图）
- 但**技术栈保留**：`kg_ppr.py` / `kg_eval_ppr.py` 已归档，换更大的评测集可直接复测
- 下一步若要验证，需要的是**更多多跳样本**（30 条测不出 3pp 以下的差异），不是继续调参

## 七、下一步（如果还要做召回）

按性价比排序，**不解决根本问题就别投入**：

1. **枢纽降权**（成本最低，半天）：扩邻居时按 `1/log(df)` 加权，
   让低频实体的边更有话语权。能缓解但**不解决**「没有关系类型」。
2. **实体链接 + 别名归一**（中等）：把「集群五大系统 / 那批系统 / 五个系统」
   映到同一实体，才能跨表述跳转。这是做关系抽取前的必要前置。
3. **关系抽取而非共现**（高成本，真正解法）：从「X 用 Y / X 依赖 Y / X 的 Y 是 Z」
   抽三元组，得到有类型、有方向的边。此时图谱才能回答「谁指向谁」。

> 结论：**1pt 投入到此为止。** 再往上做就不是 1pt 的量级了，
> 需要单独立项，且必须先回答「这个知识库的多跳问题到底有多少比例
> 真的需要跨文档推理」——如果多数只是「同一篇里没检索到」，那该修的是召回而不是图谱。
