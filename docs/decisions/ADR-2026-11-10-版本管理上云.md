## 0. 一句话结论

**生产库继续只用 `snapshot.py` + 本地 git，不上云；`kb-from-zero` 补成「Docs-as-Code + Git 单一版本真相源 + 人审发版闸门 + 云端预检」的半自动体系，默认全离线、零对外动作，push 由库主单独授权。**

不重构、不换平台、不引 Node 工具链、不启用 Git LFS。

## 1. 背景：逐字回读需求

库主原话要点（2026-11-10）：

1. 「git 只本地未推远程（等确认）」——生产库维持现状，不推。
2. 「我的之前不是用 `snapshot.py` 吗」——提醒版本管理已有轮子，别另起炉灶。
3. 「这个暂时不用上推远程仓库，我没有云端大容量的需要可以等后面再说」——**没有大容量云端需求**，不搬 19 GB 级向量库/模型/媒体。
4. 「可以在 kb-from-zero 这个仓库版本增加版本管理上云的需要」——能力建在**这个** GitHub 仓库里。
5. 「参考业界主流知识库项目和技术还有 GitHub 主流项目和技术来完善，选择最好的最完善的最合适的」——要调研、要对比、要给取舍理由，不许拍脑袋。

**判据**：能力必须**建成且可运行**，但开关（push）默认关闭；完成 ≠ 发布（AGENTS §5.12）。

### 2.2 缺口（三条，其中一条是可证伪的故障）

1. **版本号真相源分裂**（实测）：
   - `RELEASE.md` 头部：当前版本 `v1.17.1`（并同时列「图谱子系统 v1.0.1 / 检索引擎 v1.16.0 / 门户与文档 v1.4.0」）；
   - `modules/知识库索引/VERSION`：`1.16.0`；
   - `publish_to_github.bat`：`set "TAG=v1.3.1"` —— **写死在三代之前**；
   - tag 线 `v1.14.2 → v1.15.0 → v1.16.0 → v1.17.0 → v1.17.1` 实际跟的是检索引擎版本线，却被当成仓库整体版本。
   - 根级**没有** `VERSION` / `CHANGELOG.md` / `HANDOFF.md` / `CONTRIBUTING.md`。

2. **🔴 发版流水线当前是断的**（可证伪）：
   - `release.yml` 推 `v*` tag 时执行 `make_release_notes.py --version <tag> --check`；
   - 该脚本默认读 `modules/知识库索引/CHANGELOG.md`；
   - 该 CHANGELOG 里最高只有 `## [v1.16.0]`（第 51 行），**没有 v1.17.0 / v1.17.1 段**；
   - 因此推最新 tag 会被工作流**主动 fail**（"宁可不出 Release，也不出一个空版"）——这不是 bug，是门禁在正确报警：**有人打了 tag 却没写版本日志**。
   - 修法不是伪造模块日志，而是把 Release 正文来源切到**根级 CHANGELOG**，并让根 CHANGELOG 顶段版本与 tag 强制一致。

3. **没有「上云前预检」**：`publish_to_github.bat` 里隐私扫描有，但缺「版本一致性 / 待推体积 / 词表是否就位」的机械校验，且 TAG 写死。

## 3. 业界调研（2026-11-10 检索，标题 + URL + 访问日期）

### 3.1 发版自动化（GitHub 主流）

- **Keep a Changelog 1.1.0 + Conventional Commits 1.0.0** 仍是结构规范与提交语法的事实标准；`feat→minor`、`fix→patch`、`feat!→major`；分类 Added/Changed/Deprecated/Removed/Fixed/Security。来源：[Changelog Best Practices](https://github.com/simota/agent-skills/blob/main/launch/reference/release-report-writing.md)（访问 2026-11-10）。
- **工具三分天下**：`semantic-release`（全自动、Node 生态、CI 里直接发版）／`release-please`（Google，开 **Release PR** 供人审后再发版，GitHub Actions 原生，支持 `release-type: simple`，只需 `version.txt` + `CHANGELOG.md`）／`changesets`（monorepo 独立版本）。来源：[How to Implement Semantic Versioning Automation](https://oneuptime.com/blog/post/2026-01-25-semantic-versioning-automation/view)、[Conventional Commits 指南](https://devtoolsguide.com/conventional-commits-guide)、[Release Please 官方](https://github.com/googleapis/release-please/blob/eece92bfd02a493b8059e00cd766a7c7d1387cb7/README.md)（均访问 2026-11-10）。
- **单人维护 / 非 Node 项目**推荐 `release-please` 的 `simple` 型或 `git-cliff`（Rust、无需 Node）：[release-please 配置样例](https://lobehub.com/skills/dwmkerr-claude-toolkit-release-please-development)（访问 2026-11-10）。
- `standard-version` 已废弃，不再作为新项目起点。

### 3.2 知识库 / 文档形态（业界主流）

- **Docs-as-Code**（Docusaurus / MkDocs / VitePress）：Markdown 进 Git，靠 Branch/PR/Diff 做版本控制，版本控制能力「极高」，代价是编辑要会 Git。来源：[Documentation as Code: A Practical Guide](https://valoryx.org/blog/documentation-as-code)、[技术文档知识库方案对比](https://ai.qidianhudong.com/aikonw/4350.html)（访问 2026-11-10）。
- **Wiki 类**（Wiki.js / Outline / BookStack / DokuWiki）：网页所见即所得，但「内容不在 Git（或只是单向导出）、没有 PR 评审、版本历史远弱于 git」。其中 Wiki.js 2.5.x 支持 Git 后端，3.x 仍 beta 且转 PostgreSQL-only。来源：[Self Hosted Knowledge Base Tools](https://cloudraptor.io/self-hosted-knowledge-base)、[14 Top Free Open-Source Knowledge Base Software](https://www.itechguides.com/14-top-free-open-source-knowledge-base-software-best-self-hosted-tools/)（访问 2026-11-10）。
- 本仓库**已经是 Git-first docs-as-code**（`docs/` 全是 md、CI 跑校验），换平台＝推翻已有工作流，属重构，直接淘汰。

### 3.3 大文件

- Git LFS 免费额度 1 GB 存储 + 1 GB/月带宽；已入库的大文件**必须重写历史**才能迁 LFS，会打断所有 clone；CI 需 `lfs: true` 且容易烧配额。来源：[Managing Large Files in Git](https://www.grizzlypeaksoftware.com/library/managing-large-files-in-git-lfs-and-alternatives-5es04krf)、[Git LFS Best Practices](https://codeloomdevv.co.in/blog/git/git-large-file-storage-tutorial)（访问 2026-11-10）。
- 库主明确「没有云端大容量的需要」→ **重资产留在本地快照，不上云，不启用 LFS**；LFS/DVC 记为未来可选项，不默认开。

### 3.4 候选对比表

| 方案 | 版本真相源 | 人审闸门 | 依赖 | 与现状冲突 | 结论 |
|---|---|---|---|---|---|
| A. `semantic-release` 全自动 | CI 推算 | **无**（push 即发版） | Node + 多插件 + secrets | 绕过「上传云端先问」「人验签字」红线 | ❌ 淘汰 |
| B. `release-please` (simple) | `version.txt` + CHANGELOG | **有**（Release PR） | GitHub Action（云端） | 会在 push 时自动开 PR，仍属自动对外动作 | ⚠️ 取其**规范**，暂不启用 Action |
| C. 移植生产库 `snapshot.py` | VERSION + `_versions/` 磁盘快照 | 有（手工） | 0 | Git 已是完整历史，再全量复制＝冗余；且会把重资产带进仓库 | ❌ 不移植全量快照，只迁移**决策理由/CHANGELOG 骨架/HANDOFF 习惯** |
| D. Git LFS / DVC | 指针文件 | 有 | 配额 + 重写历史 | 无云端大容量需求 | ❌ 不启用，记为可选项 |
| E. 换 Wiki.js / Docusaurus | 数据库或另一套构建 | 有 | 服务/构建链 | 推翻现有 docs/ + CI | ❌ 重构，淘汰 |
| **F. 本地半自动闸门（本方案）** | **根 `VERSION` 唯一** | **有**：`--check` + `--preflight` + 人签字后才 push | **0 第三方**（标准库 Python） | 只增文件 + 修 2 处既有 bug | ✅ **选中** |

**为什么 F 最合适**：它同时满足「能力建成」「默认零对外动作」「不重构」「零新增依赖」「保留现有好的 release.yml」；B 的规范（Conventional Commits / Keep a Changelog / Release PR 思路）以**文档 + 本地脚本**的形式吸收，等库主明确要自动发版时，只需加一个 workflow 即可升级到 B，不必推倒重来。

## 4. 选型与五何

**为何做**：不加这一层，推最新 tag 必被 `release.yml` 拒发（§2.2 第 2 条实证），且 `publish_to_github.bat` 还在发 v1.3.1；不做代价是「版本号没人信、发版靠记忆」。

**为何这样**：见 §3.4 对比。核心取舍是**把「自动化程度」让给「人审红线」**——库主规则要求上传云端先问、人验签字、零对外动作，所以选半自动而非全自动；把「全量磁盘快照」让给「Git 本身即历史」，所以不移植 snapshot.py 的复制逻辑。

**边界在哪**：
- 不 push、不建远程仓库、不发 Release、不打远程 tag；
- 不改生产库任何内容（生产库继续 `snapshot.py` + 本地 git，无 remote）；
- 不把隐私词表、真实路径、真实项目名、媒体/向量库/模型带进仓库；
- 只增文件 + 修 2 处既有 bug（`release.yml` 的 CHANGELOG 来源、`publish_to_github.bat` 的写死 TAG），不删任何东西。

**怎么验**：`tools/release_gate.py --check`（版本一致性）、`--preflight`（隐私 + 待推体积）、`--bump --dry-run`（只打印不写）、`privacy_scan.py --git-only` 0 BLOCK、`git status` 可查；CI 新增 `version-check.yml` 跑同一份 `--check`。**校验人 = 库主**（AI 不代签）。

**何时停**：任一门禁 rc≠0 立即停；要 push 时必须由库主单独授权，脚本本身永不执行 push。

## 6. 验收判据与人验包

**机械判据（可复跑）**：
```
python tools/release_gate.py --check              # rc=0：VERSION == 根 CHANGELOG 顶段 == 最新 tag
python tools/release_gate.py --preflight          # rc=0：隐私 0 BLOCK + 待推体积清单
python tools/release_gate.py --bump patch --dry-run   # 只打印、不写盘
python tools/make_release_notes.py --version 1.17.1 --changelog CHANGELOG.md --check
python tools/privacy_scan.py --git-only
git status --short
```

**人验包六件**（§5.12）：改动清单 = 上表 9 项｜diff = `git diff` 全文｜可复跑命令 = 上面 6 条｜验收取证 = 各命令 rc 与输出｜边界 = §7｜一键回退 = `git revert <本轮 commit>`（未 push 前可直接 `git reset --soft HEAD~1`）。
**六步 SOP**：① 看 diff ② 跑 `--check` ③ 跑 `--preflight` ④ 跑 `--dry-run` ⑤ 目检根 CHANGELOG 的「决策理由」是否属实 ⑥ 回 `ok` 才算确认收口（**不等于人已验签字**）。

## 8. 回退

本轮未 push，回退成本为零：
```
git -C <仓库根> log --oneline -3        # 找到本轮 commit
```
