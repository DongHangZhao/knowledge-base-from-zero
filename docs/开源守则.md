# 开源守则：我是怎么从一堆现成许可里挑出 KBL-1.0 的

**简体中文** ｜ [English](open-source-policy.en.md)

> 面向想「开放但不想被白嫖商用」的独立作者。
> 结论先行：**没有一份现成许可同时满足「禁止商用 + 强制署名 + 覆盖代码与文档 + 有中文权威文本」**，
> 所以基于成熟许可拼了一份自己的：**KBL-1.0**。

---

## 一、先想清楚：你到底想让别人做什么

选许可不是选立场，是选**边界**。先回答四个问题：

| 问题 | 我的答案 | 直接决定 |
|---|---|---|
| 别人能免费看、学、自己用吗？ | 能，越多人搭起来越好 | 必须授予复制/修改/自用权 |
| 别人能拿去卖钱吗？ | 不能 | 必须禁商用 |
| 别人转载/二创要提我吗？ | 必须提，还要给出处 | 必须加署名条款 |
| 别人改完能换成 MIT 再发吗？ | 不能，否则署名会被洗掉 | 必须加相同方式共享 |

四个答案定下来，能选的许可范围其实已经很窄了。

## 二、逐个排除：我参考过的六类方案

GitHub 上主流项目的做法大致六类，我逐个试了一遍：

### 1. MIT / Apache-2.0 / BSD —— 直接排除

GitHub 上占比最高的选择，也是绝大多数「工具库」的默认答案。

- ✅ 生态最友好，公司敢用，律师不用审
- ❌ **明确允许商用、允许闭源、允许去掉署名后重发**
- ❌ 与「不可商用 + 标注出处」两条硬诉求正面冲突

> 典型反例：你把项目 MIT 出去，第二天就有人在淘宝卖你的模板，你连投诉的立场都没有。

### 2. GPL-3.0 / AGPL-3.0 —— 排除

很多人以为 GPL 能挡商用，这是误解。

- ✅ 强制衍生作品开源（copyleft）
- ❌ **不禁止商用**，只要求开源。别人照样可以卖，只要把源码一起给
- ❌ AGPL 只多加一条「网络服务也要开源」，仍然不挡卖

> 想挡商用，GPL 系全部无效。

### 3. CC BY-NC 4.0 / CC BY-NC-SA 4.0 —— 部分可用，但不适合代码

知识共享的「非商业」版本，文档圈最常用。

- ✅ NonCommercial 定义成熟，国际通用，有官方中文译本
- ✅ BY（署名）+ SA（相同方式共享）正好对上我的诉求
- ❌ **CC 明确不建议用于软件**：没有专利授权条款、没有源码分发条款、与 GPL 等不兼容
- ❌ 本仓库是「代码 + 文档」混合体，只套 CC 会留下代码侧的授权空白

### 4. PolyForm Noncommercial 1.0.0 —— 结构最好，但只保声明不保署名

专为「软件 + 文档 + 内容」设计的非商用许可，结构是我见过最严谨的。

- ✅ 定义清晰（Noncommercial Purposes / Personal Uses / Noncommercial Organizations 分三层写）
- ✅ 明确允许个人研究、实验、业余项目、慈善/教育/政府机构使用
- ✅ 条款颗粒度细，可执行性强；有 SPDX 标识 `PolyForm-Noncommercial-1.0.0`
- ✅ 有 `Notices` 条款：分发时必须带上许可文本/URL + 原始 `Required Notice:` 行
- ❌ **但 Notices 只是「保留声明」，不是「公开署名」**：
  它管的是「别把版权信息删掉」，不管「你写文章/做视频讲这套东西时要不要提作者」。
  而我要的恰恰是后者——**转载、讲课、二创都要标出处**。
- ❌ 无官方中文文本，中文用户容易误读「noncommercial」的范围

> 这一条是我最后决定自己写许可的直接原因：**保留声明 ≠ 强制署名**。
> 前者防止版权信息被抹掉，后者才让人知道「这东西是谁做的」。

### 5. 源码可用（source-available）商业许可 —— 参考边界写法

Elastic License 2.0、Business Source License 1.1、Sustainable Use License（n8n）、
Commons Clause 这类「不是开源但源码公开」的许可，我主要参考它们**怎么划商业边界**：

- Elastic License 2.0：禁止「把软件作为托管服务提供」——表述精准
- BSL 1.1：时间锁（若干年后自动转开源）——思路好，但个人项目用不上
- Sustainable Use License：禁止「与作者的产品竞争」——主观性太强，不好执行

我从这里学到的是：**禁商用不能只写一句「不可商用」**，必须把
SaaS、付费咨询、打包进付费产品、作为训练数据这些现实场景逐条列出来，
否则真出事时全靠解释。

### 6. 自定义许可 + 中文对照 —— 最终走的路

GitHub 官方文档明确支持自定义许可（`LicenseRef-*` 命名），只是不会显示绿色徽章。

- ✅ 三条硬诉求可以一次写全
- ✅ 中英文双版，中文优先，对国内读者无歧义
- ❌ GitHub 侧栏会显示「Unknown license」，需要 README 里显式解释
- ❌ 无法享受 OSI 生态的「默认合规」信任

## 三、KBL-1.0 = 三家之长

最终方案是拼接，不是发明：

| 来源 | 借用的是什么 |
|---|---|
| **PolyForm Noncommercial 1.0.0** | 整体骨架：定义 → 授权 → 条件 → 禁止 → 终止 → 免责，以及 Noncommercial / Commercial Purpose 的定义写法 |
| **CC BY-NC-SA 4.0** | 署名机制（BY）与相同方式共享（SA）：署名通知要包含什么、放在哪里才算数 |
| **Elastic License 2.0 / SUL** | 商业禁止的逐条列举方式（8 种典型场景 + 30 天评估期） |
| **GPL-3.0** | 终止与补救机制（违约自动终止 + 30 天 cure 期恢复） |

三条硬诉求对应的条款：

| 诉求 | 落在哪 |
|---|---|
| **不可商用** | 第 4 条（8 项禁止 + 30 天评估窗口）+ 第 5 条（商业授权通道） |
| **必须署名** | 第 3.1 条（保留声明）+ 第 3.2 条（署名通知五要素 + 放置位置） |
| **标注出处** | 第 3.2 条 (d) 原链接 + 第 3.4 条（禁止改宽松许可洗署名） |

## 四、一个关键取舍：为什么不干脆用 CC BY-NC-SA

如果本仓库**只有文档**，我会直接用 CC BY-NC-SA 4.0，理由充分、国际认可。

但它是**代码 + 文档混合**：

- `kb-hub/` 是可运行程序 → 需要源码分发、专利、担保免责的软件级条款；
- `templates/` `docs/` 是文档 → 需要署名与相同方式共享；
- `kb-hub.exe` 是二进制 → 需要说清 PyInstaller / Python 的第三方许可关系（见 `NOTICE` 第 3 节）。

一份许可同时覆盖三者，比「代码 CC0 + 文档 CC BY-NC-SA + exe 另说」清晰得多——
**用户不该为了合法使用一个仓库去读三份许可**。

## 五、守则落地：三件事你已经自动获得

用这套体系时，你**不需要**做任何事（自用、非商业、不传播）。

一旦要传播，只需要记住三句话：

1. **提名字**：FallenPetal · knowledge-base-from-zero
2. **给链接**：原始仓库地址
3. **说改了什么**：一句话即可（仅衍生作品需要）

模板复制即用 → 见 [`NOTICE`](../NOTICE) 第 1 节（仓库 / 文章 / 视频 / 应用四种场景）。

## 六、常见疑问

**Q1：公司内部用来搭知识库，算商用吗？**
看你是否在生产环境长期使用。许可第 4 条给了 **30 天评估期**（不进生产、不产生收入）。
超过就属于「组织内部生产环境部署」，需要商业授权。个人学习不受此限。

**Q2：我在公司做内部分享，讲这套方法，收费吗？**
不向听众收费 → 非商业，允许，附署名即可。
公司为此向你收费或作为付费培训售卖 → 商业用途，需要授权。

**Q3：我可以 fork 后改成自己的名字发吗？**
可以 fork，**不能去掉原作者署名**（第 3.2、3.4 条）。正确做法是保留原署名 + 注明「已修改」。

**Q4：我把代码读了一遍，用自己的话重写了一遍，还受约束吗？**
思想与方法不受著作权保护，**具体表达**受保护。如果你只是借鉴方法论、完全独立实现，
不受本许可约束；但建议仍标注「方法参考自……」——这是体面，也是引用规范。

**Q5：为什么 GitHub 显示 Unknown license？**
自定义许可不在 GitHub 的许可识别库里。这是预期行为，README 顶部有显式说明。
如果你在意绿色徽章，可以换 PolyForm Noncommercial（会识别），代价是丢署名条款。

**Q6：这份许可有法律效力吗？**
它是著作权许可合同，在多数法域有效。但**作者不是律师**，这也不是法律意见。
真要商用或发生纠纷，请双方各自咨询律师。

**Q7：我能用它训练 AI 模型吗？**
商业模型的训练数据 → 禁止（第 4 条 g 项）。个人研究用途的模型训练 → 允许。

## 七、给想写自己守则的人：一份检查清单

按顺序过一遍，半小时能定：

- [ ] 1. 列出「允许 / 禁止」各 5 条最在意的场景（不要写抽象词，写具体动作）
- [ ] 2. 判断作品类型：纯代码 / 纯文档 / 混合 / 含二进制产物
- [ ] 3. 先看现成许可能不能覆盖 80%：MIT（无所谓）→ Apache-2.0（要专利条款）→ GPL（要 copyleft）→ CC BY-NC-SA（文档非商用）→ PolyForm NC（软件非商用）
- [ ] 4. 只对剩下的 20% 做增补，别从零发明
- [ ] 5. 把「商业用途」写成**可判定的动作清单**，不要只写一句「禁止商用」
- [ ] 6. 署名条款必须写清**五要素 + 放置位置**，否则无法执行
- [ ] 7. 加相同方式共享，否则署名会被下游洗掉
- [ ] 8. 写终止与补救（30 天 cure），给自己和对方都留台阶
- [ ] 9. 中英双版，明确冲突时以哪版为准
- [ ] 10. 第三方依赖单独列 NOTICE，别混进主许可
- [ ] 11. README 顶部用一句话说清「能做什么/不能做什么」，别让人去读 150 行英文
- [ ] 12. 发布前跑一次隐私扫描（`tools/privacy_scan.py`），别让守则成了笑话

## 九、一句话总结

**MIT 是「随便用」，GPL 是「用了就得开源」，CC BY-NC 是「不能商用但要署名」，**
**KBL-1.0 是「不能商用 + 必须署名 + 不许洗署名 + 文档代码二进制一把管」。**

选它不是因为更先进，是因为它刚好对上我要守的那条线。
