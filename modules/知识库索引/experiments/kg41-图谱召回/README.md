# #41 图谱召回实验 —— 完整记录

> 状态：**v1 FAIL / v2 FAIL / v3 抽取修好了、召回仍然 FAIL** → 已归档，不进生产
> 结论一句话：**共现图谱适合"看"，不适合"召回"。** 详见第 4 节。

## 1. 要回答的问题

多跳问题（"那批系统里第一个上线的那套，除了关系库还用了哪种库"）需要
先定位到总览页、再跳到子文档。单轮向量检索一次只能命中一篇，所以想问：

> **用「实体共现邻居」做 1-hop 扩展，能不能把第二跳的文档拉进 Top5？**

判据（实验前定死，不允许事后改）：
- 主指标：`all@5`（**所有** gt 都进 Top5），不是 `any@5`
- 要求：`all@5` 相对基线 **≥ +3pp**，且 p95 延迟增幅 ≤ +150ms

## 2. 为什么必须用 all@5 而不是 any@5

这是本实验最重要的一条方法学，踩过坑：

多跳集的每条题有 **2~3 个 gt**（第一跳总览 + 第二跳答案）。
`eval_rag` 原本的 Recall 口径是 **任一 gt 命中即算 hit**。
于是第一次跑出来：

```
baseline any@5 = 100%    treat any@5 = 100%    Δ = 0
```

差点据此收工，结论"图谱无害也无用"。
**真相是 any@5 已经封顶，任何改进都不可能显现。**

换成 all@5（全部 gt 都要命中）：

```
baseline all@5 = 50.0%   ← 立刻露出天花板下面的空间
```

> 教训：**多答案评测必须用「全命中」口径**。任一命中口径在
> gt≥2 的集合上会饱和到 100%，把真实差异全部吃掉。

## 3. 三轮实验数据

沙盘：`state/_kg_sandbox.db`（生产库的完整副本，4.7GB，实验绝不写生产）。
评测集：`state/kb_eval_multihop_30.json`（30 条，2 跳 22 条 / 3 跳 8 条，锚点已加）。

| 轮次 | 抽取方式 | 中文实体占比 | 短语整体保留 | baseline all@5 | treat all@5 | Δ |
|---|---|---|---|---|---|---|
| v1 | `jieba.cut` 直抽 | 7.8% | 0/6 | 50.0% | 46.7% | **−3.3pp** |
| v2 | + 词性 + df 过滤 | 69.9% | 0/6 | 50.0% | 46.7% | −3.3pp |
| v3 | **+ 领域词典注入** | 70.5% | **5/6** | 50.0% | 43.3% | **−6.7pp** |

### 3.1 v1 的失败根因（已定位，值得记住）

`jieba.cut("集群五大系统项目里…")` → `['集群','五大','系统','项目',...]`

"系统"被 df 过滤掉（太泛），剩"集群""五大"这种碎片去扩邻居，
召回的是**求职简历**。所以 v1 的 −3.3pp 不是"图谱无效"，
而是"起点就是错的"——**这是假阴性**。

### 3.2 v3 把抽取修对了

做法（`kg_terms.py`）：从 7524 篇文档标题挖领域词典（分隔符 + 括号），
注入 jieba 后再分词。实测：

```
注入前：集群 / 五大 / 系统 / 项目
注入后：集群五大系统项目          ← 整体保留
```

关键短语 5/6 整体保留（集群五大系统项目 / 全院统一预约平台 /
智能血液透析信息系统 / 可复用模块 / 集群五大系统）。

### 3.3 抽取修对了，召回反而更差 —— 这才是核心发现

v3 的 treat 组 all@5 是 43.3%，比 v1 的 46.7% 还低。
且**权重实验**证明不是"排不进 Top5"的问题：

| KB_W_KG（图谱路权重） | baseline all@5 | treat all@5 | Δ |
|---|---|---|---|
| 0.5（默认） | 50.0% | 43.3% | −6.7pp |
| 1.0 | 50.0% | 43.3% | −6.7pp |
| 1.5 | 50.0% | 40.0% | −10.0pp |
| 2.5 | 50.0% | 30.0% | **−20.0pp** |

**权重越高越差，单调恶化。** 如果只是"扩展结果排序不够靠前"，
提高权重应该能翻盘。单调恶化说明：**扩进来的内容是错的**，
权重越大，错的东西挤掉对的东西越多。

## 4. 根因：共现 ≠ 相关

`expand_1hop` 的机制是"找共享实体的 chunk"。问题在于：

- 「集群五大系统」这个实体的 **df 很高**（几十篇文档都提它）
- 所以它的一跳邻居 = **半个语料库**
- 扩展结果里绝大多数是"提到过这个系统"的文档，**不是答案所在的那一篇**

一句话：**枢纽实体的邻居没有区分度。**
1-hop 共现在"高频枢纽词"上必然失效，而多跳问题的第一跳锚点恰恰总是枢纽词。

这不是调参能解决的，是机制层面的：

| 想要的 | 共现图谱能给的 |
|---|---|
| "A 的数据库字段指向 B" | "A 和 B 出现在同一段" |
| 有方向、有类型的关系 | 无向、无类型的关联 |
| 可判定（查得到/查不到） | 只能算权重 |

## 5. 那图谱还有用吗——有，但不是这个用法

**有用的地方**（已交付）：
- 知识库结构诊断：哪些概念是枢纽、哪些是孤岛
- 可视化：一眼看出知识库的主题分布与薄弱区

**无效的地方**（本实验证明）：
- 当召回增强通道

**如果要继续做召回，必须换机制**（下一步方向，按优先级）：
1. **关系抽取而非共现**：从"X 用 Y / X 依赖 Y / X 的 Y 是 Z"这类句式抽
   三元组，得到有类型、有方向的边
2. **实体链接 + 别名归一**：把"集群五大系统""那批系统""五个系统"映到同一实体，
   才能跨表述跳转
3. **枢纽降权**：扩邻居时按 `1/log(df)` 加权，让低频实体的边更有话语权
   （成本最低，可以先试，但不解决"没有关系类型"的根本问题）

## 6. 怎么复跑

```bash
PY=E:/_venvs/gpu/Scripts/python.exe
cd modules/知识库索引

# 0) 必须有沙盘副本（脚本会拒绝在 kb.db 上建侧表）

# 2) 跑对照（all@5 口径，一次出 baseline 与 treat）
export KB_BGE_MODEL_DIR=<生产>/models/bge-small-zh

KB_W_KG=1.5 $PY -u experiments/kg41-图谱召回/kg_eval_both_hit.py ...
```

## 8. 一句话给未来

> 别再花时间调 1-hop 的权重和 topk 了。**共现图谱的瓶颈在机制不在参数**：
> 它无法表达"谁指向谁"。要么升级成关系抽取，要么就只把它当"看"的工具用。
