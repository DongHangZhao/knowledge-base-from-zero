## Purpose

Turn the Markdown under `wiki/` into a SQLite FTS5 index so AI can "retrieve first, answer second",
with every conclusion carrying a file path instead of a path invented from memory.

This is **Pipeline B (index pipeline)** in the architecture: `md → kb.db`, a derived layer you can delete and rebuild.

## Usage

```bash
python modules/retrieval/build.py                    # incremental build (run after every md edit)
python modules/retrieval/build.py --full             # full rebuild (after changing the tokenizer)
python modules/retrieval/search.py "keyword" --topk 5  # search
python modules/retrieval/db_admin.py health          # health check
python modules/retrieval/db_admin.py backup --keep 8  # backup (VACUUM INTO, never a plain copy)
```

## Call chain

```
scan(md) → compare hash → unchanged: skip / changed: rewrite
        → docs (metadata) + docs_fts (whole-document inverted index)
        → split_chunks (by heading level) → chunks + chunks_fts
search(query) → whole-doc ⊕ chunk → RRF fusion → resolve to doc.path
```

## Pitfalls

1. **FTS5 external-content tables cannot be DELETEd directly** → use a normal FTS5 table (self-contained content).
2. **SQL comments can only use `--`**; `#` is a syntax error.
3. **Changing the tokenizer requires `--full`**, otherwise build-time and query-time tokenization diverge: hit rate halves and nothing errors.
4. **You cannot `cp kb.db` in WAL mode** → use `VACUUM INTO`.
5. **Chunks alone are a negative optimization** (they lose whole-document term frequency); always fuse with whole documents.

## Verification

- Run `build` twice; the second run must be entirely "unchanged";
- Delete one md and build again: it disappears from the index;
- Pick three random results and paste each `path` into a file manager — **they must exist**;
- Ask an in-base question: AI answers with a path. Ask something outside: it says "not in the knowledge base".
